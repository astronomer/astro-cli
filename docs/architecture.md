# Architecture

Astro CLI 2.0 is the second major version of the Astro CLI. Its centerpiece is `astro local`, a local-Airflow command family that replaces the `astro dev` tree, built on a `pyproject.toml` manifest.

This page holds the rules the code agrees on: the layers, the sub-module boundaries, the output contract, and where local state lives. The other docs:

- [manifest-reference.md](manifest-reference.md): every key in `pyproject.toml`.
- [secrets.md](secrets.md): local environment values, the vault, and how they reach Airflow.
- [workspace-link.md](workspace-link.md): reading values from a linked Astro workspace.
- [instances.md](instances.md): which Airflow a command talks to.
- [deploy.md](deploy.md): `astro deploy` and `astro package`.
- [install.md](install.md): installing the CLI and converting a project made by Astro CLI 1.x (a 1.x project).

## One core, three consumers

The CLI is a library that ships a binary. Three consumers share the core:

1. the `astro` binary (this repo);
2. Astro Desktop, a desktop app for local Airflow development, which imports the `pkg/*` sub-modules as Go modules;
3. editor integrations, which shell out to the CLI and read `--output json` (see [Output](#output)).

Anything a second consumer needs lives in `pkg/` as a sub-module. `internal/` holds CLI-private glue: plan building, resolution order, cobra wiring. Some functions in `pkg/*` are called only by Astro Desktop, which is why `make deadcode` skips the sub-modules.

## Layers

```
cmd/        parses flags, calls one function, formats output. Nothing else.
internal/   CLI-private logic. May import pkg/. Never imports cmd/.
  platform/ one directory per control plane (astro, apc), each holding that
            platform's domain packages and the transport they talk through.
pkg/        shared sub-modules, plus ordinary root-module packages.
```

Only the `pkg/` directories with their own `go.mod` are sub-modules. The rest are ordinary packages in the root module.

### Core and shell

The rules divide the code in two, after "functional core, imperative shell". The **core** returns data and typed errors and leaves the I/O to its caller: `cmd/local`, `cmd/cliout`, and the packages below `cmd/` that archlint lists as core. The **shell** does the I/O itself: it prints, prompts and reads `config/`. It is mostly code inherited from Astro CLI 1.x, such as the rest of `cmd/` and both control-plane platforms under `internal/platform/`. Shell code may import the core; the core never imports the shell's `cmd` tree.

Logic that is not about one platform does not import `internal/platform/`. It takes an interface and `cmd/` wires the implementation, so `internal/deploy` reads the same whichever control plane it ships to. The seams that may reach a platform are `internal/emenv` and `internal/instancelocate`. The core packages do not read `config/` either, except the four config readers `internal/astrosession`, `internal/containercfg`, `internal/emenv` and `internal/instancelocate`.

Below `cmd/`, the core never prints and never exits. Libraries report progress through callbacks (`localrt.Callbacks`) and return typed errors; each frontend decides how to render. The CLI writes text, desktop draws UI.

[`internal/archlint`](../internal/archlint/archlint_test.go) enforces these rules as tests:

| test | rule |
| --- | --- |
| `TestInternalNeverImportsCmd` | nothing under `internal/` imports `cmd/` |
| `TestCorePackagesNeverImportConfigOrShellCmd` | `cmd/local`, `cmd/cliout` and the core packages stay off `config/` and the shell `cmd` tree |
| `TestOnlyTheSeamsReachIntoAPlatform` | only the seams import `internal/platform/` |
| `TestEveryInternalPackageIsAccountedFor` | every `internal/` package is listed as core, a core config reader, or shell |
| `TestCorePackagesBelowCmdNeverPrintOrExit` | no `fmt.Print*`, `os.Exit` or `log.Fatal*`/`Panic*` in core packages below `cmd/` |
| `TestEveryPkgSubmoduleIsLinted` | every `pkg/*/go.mod` is in the Makefile's `LINT_SUBMODULES` |
| `TestEveryLintedSubmoduleIsHeldToTheNoPrintRule` | every linted sub-module is under the no-print rule |
| `TestTheAuthDoorsStayOptional` | `pkg/instances` and the instance locators link neither auth door nor a cloud SDK |
| `airflowkey_test.go` | `[tool.astro]` carries no Airflow-version field, and nothing reads one |

Contract structs (`Plan`, `Deps`, options) pass by value, so the `hugeParam` lint is suppressed for the packages that carry them (the path list is in `.golangci.yml`).

## Sub-module rules

A `pkg/` sub-module:

- has its own `go.mod` (`module github.com/astronomer/astro-cli/pkg/<name>`);
- imports neither the parent module nor a sibling sub-module, except the declared dependencies below; if it needs a path or a config value, it takes it as an argument;
- keeps its dependency list near-empty, since every dependency is one desktop inherits;
- is wired into the root module with a require + replace pair, added with its first in-repo consumer, and listed in `LINT_SUBMODULES`.

If a candidate cannot be made into a self-contained sub-module in an afternoon, it belongs in `internal/` instead.

### Declared sibling dependencies

A sub-module may import a sibling only when a second implementation of what the sibling owns would be a second answer to the same question. Each one is listed here; a new one is added here, not assumed. archlint does not check this list, so review does.

| module | may import | why |
| --- | --- | --- |
| `airflowenv` | `connmodel` | the codec exists to encode the connection type |
| `envschema` | `airflowenv` | declared names are validated with `ValidEnvKey`, `ValidVarKey` and `ValidConnID`, and encoded as `AIRFLOW_VAR_`/`AIRFLOW_CONN_` keys by the same rules |
| `connwarehouse` | `connmodel`, `fsatomic` | it maps a connection into an entry of `~/.astro/agents/warehouse.yml`, written atomically |
| `secrets` | `fsatomic` | atomic value writes, the link index, and its lock |
| `proxy` | `fsatomic`, `airflowrt` | atomic writes of `routes.json` and the daemon record; and `airflowrt` owns the local Airflow's provisioned account, which the proxy logs in with so a project opens without Airflow 2's login page |
| `localrt` | `airflowrt`, `container`, `fsatomic`, `manifest`, `proxy`, `uv` | it orchestrates the runtime primitives (PID files, env, health), routes, the container engine, venvs and atomic state. It reads two manifest fields: `[tool.uv] environments`, to stop before uv on a platform the project leaves out, and `[tool.uv] constraint-dependencies`, passed to `uv pip install` on a hot install, because an embedder that sets `UVOptions.NoConfig` makes `uv pip` skip them |
| `imagebuild` | `localrt/rt`, `manifest`, `runtimeversions`, `airflowrt` | it reports progress in the runtime's vocabulary (`Callbacks`, `LogLine`), through the dependency-free `rt` leaf rather than `localrt`; drops the Airflow requirements with `manifest.WithoutAirflow`; names an Airflow 2 base from the runtime catalog; and reads build-secret mounts with `airflowrt.SecretMounts` |
| `checks` | `manifest`, `platformversions` | `manifest.WithoutAirflow`, and the table of Airflow versions MWAA and Composer offer |
| `scaffold` | `manifest` (with `tomledit`), `envschema`, `airflowenv`, `connmodel`, `fsatomic`, `secrets`, `runtimeversions`, `airflowrt` | it writes the manifest (`EditManifest`, the one writer of an existing `pyproject.toml`, atomically) and must agree with its parser; it writes `[tool.astro.env]` declarations with the parser's own grammar (`envschema.DeclarationName`, `DeclarationTable`); converting a 1.x project carries its `airflow_settings.yaml` values into the vault through a caller-scoped `SecretWriter` speaking `secrets.Kind` and `secrets.Key` (it never opens a store, so the keyring stays out); it reads the runtime catalog's fallback series, `requires-python` and Astro build without fetching; and it reads a Dockerfile's `FROM` exactly as Docker mode does (`airflowrt.ReadDeclaredBase`). `uv` is test-only |
| `instances` | `manifest`, `airflowapi`, `airflowrt` | a link is manifest data; it produces `airflowapi`'s `Transport` and `CredentialSource`; and `airflowrt` owns the local Airflow's provisioned account |
| `instancelocate` | `instances`, `googleauth` | it resolves an `Instance`, and reading a Composer address needs Google credentials. Only the Composer half lives here; the Astro half needs the login context and lives in `internal/instancelocate` |
| `awsauth`, `googleauth` | `instances`, `airflowapi` (and, test-only, `manifest`) | each is an auth door implementing an `instances.Provider` |

The auth doors are separate modules so that requiring `pkg/instances` costs neither the AWS nor the Google SDK. The dependency runs one way: the core never imports a door (`TestTheAuthDoorsStayOptional`).

A dependency's own `replace` lines are never honoured, so a consumer of a module with sibling dependencies needs a require + replace pair (and a `go.work` `use`) for each sibling too.

`pkg/scaffold` also builds the prompt that hands an Airflow upgrade to Otto (`AirflowUpgradePrompt`), so `astro local upgrade airflow --with-otto` and Astro Desktop send Otto one text.

### Formats with readers outside this repo

- **`pkg/proxy`'s `routes.json`.** astro 1.x CLIs in the field write and read it and never auto-update. Add fields freely; a reshape means a new file. The v2 state record is the source of truth, and `routes.json` is a compatibility view.
- **Keyring service names and on-disk secret formats.** After the first public release, users' existing data constrains them: a change needs a migration that keeps the old name or format readable for at least one release.

### Code conventions

- Tests match the package they are in. testify and plain `testing` both exist; don't rewrite either style, and don't mix them within a package.
- Tests do not read the shell they run in, or touch the machine. A test package's `TestMain` calls `testenv.Isolate()` ([`pkg/testing/testenv`](../pkg/testing/testenv/testenv.go), the root's front for the shared [`pkg/testenv`](../pkg/testenv/isolate.go) module), which unsets the variables that change what the CLI does (`ASTRO_API_TOKEN`, `ASTRO_DOMAIN`, `ASTRO_HOME`, `ASTRO_ORGANIZATION`, `ASTRONOMER_KEY_ID` and `_SECRET`, `CI` and the other CI markers, ...), so a developer's exported token or a CI runner's `CI=true` fails nothing, and moves HOME into a temporary directory (see [Tests never touch the machine](#tests-never-touch-the-machine)). A test that needs one of the variables sets it with `t.Setenv` (`testUtil.UseAPIToken` for a token); a new variable the CLI reads is added to the list in `testenv`. Package-level fixtures are read-only: a test that needs a different one builds its own rather than reassigning the shared one, which would leak into the next run under `-count`.
- Windows handling uses build tags only when code won't compile cross-OS, and a `runtime.GOOS` switch when picking a value.

## Tests never touch the machine

A test run must not read or write the developer's own state. It happened: a test helper replaced the access token in a developer's real `~/.astro/config.yaml`, and runs under a redirected HOME made macOS ask, repeatedly, for a keychain to store `master-key` in. So a test binary is hermetic by construction, and the exceptions are guards that fail loudly rather than conventions.

**The isolation.** Every test package's `TestMain` is `testenv.Main(m)`, or, where it does more around `m.Run`, `finish := testenv.Isolate()` and `os.Exit(finish(m.Run()))`. The isolation is one module, `pkg/testenv`, with no dependency, shared by the root module (through `pkg/testing/testenv`, which adds the `pkg/secrets` keyring hooks) and by every `pkg/*` module and `e2e`, so there is one copy to fix. `Isolate` (and `Main`, which is it plus `m.Run` and the exit) makes one temporary directory per test binary and sets `HOME` and `ASTRO_HOME` (the same directory, as when `ASTRO_HOME` is unset), `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` and `XDG_DATA_HOME` (and `USERPROFILE`, `APPDATA` and `LOCALAPPDATA` on Windows) inside it; `finish` removes it. It runs the `testenv.AfterIsolate` hooks: `config` works out `HomePath`, `HomeConfigPath` and `HomeConfigFile` from the real home when it loads (go-homedir caches that home), so it registers a hook (`config/config_test_utils.go`) that drops the cache and works them out again in the isolated home, and stops the run if any is outside the temporary directory. Nothing that reads them before `InitConfig` reaches the real `~/.astro`. It pins the go command's own `GOPATH`, `GOCACHE`, `GOMODCACHE` and `GOENV` to what `go env` said before HOME moved, so a test that runs `go list` finds the module cache and honors `go env -w`. Tests that need a config build one (`testUtil.InitTestConfig`); none may rely on the machine having one, and a test that does fails on a clean machine and in CI.

**The keyring.** `Isolate` calls `secrets.MockKeyringForTests()`, which is `keyring.MockInit()` plus the record `pkg/secrets` keeps that go-keyring's default provider is in memory. A test that wants a keyring that fails calls `keyring.MockInitWithError` and restores `keyring.MockInit` in `t.Cleanup`, never the real provider, which cannot be restored. `pkg/secrets` refuses the OS backend inside a test binary that has not declared the mock: `osKeyring` (and so the `timeoutKeyring` around it) answers "tests must not use the OS keychain; call keyring.MockInit" instead of calling go-keyring (`testing.Testing()`, as `pkg/input/testsupport.go` does). A test that bypasses the mock fails; it does not prompt.

**uv.** `UV_PYTHON_INSTALL_DIR` is `$TMPDIR/astro-test-uv-<uid>/python` for every test binary: private (made with `Mkdir`, then `Lstat`ed: a real directory owned by this user and closed to others, else the run stops before anything is made), shared and persistent, so the tests that install a Python (`cmd/local`) download it once, and outside HOME, so nothing goes to `~/.local/share/uv`. uv's download cache needs no setting: the CLI pins `UV_CACHE_DIR` under the cache home, which is the temporary one.

**The guard on the real config.** Before the run `Isolate` records whether the real `~/.astro/config.yaml` and its `.lock` file exist, and each one's mtime and size, from the HOME and `ASTRO_HOME` the shell had (by `stat`, never by reading). After `m.Run`, if either differs, `finish` says what changed on stderr. It fails the package (returns 1, even though its tests passed) when `CI` is set or `ASTRO_TEST_STRICT_REALCONFIG=1`, and otherwise only warns, because a real `astro login` in another terminal changes the file too and must not fail every package on a developer's machine. Any refusal of the OS keychain fails the package in every mode. `e2e` gets the same guard through `testenv.Options{KeepHome: true}`. `CI` is read by the rule `pkg/input` uses (spaces ignored; only empty, `0` and `false` are off), and a root test holds the two together.

**Helper processes.** A test that re-executes the test binary (`-test.run=^TestSomeHelper$`) as a second CLI process passes `os.Environ()` on, which carries the isolated HOME and `ASTRO_TEST_ISOLATED_HOME`. A helper's `Isolate` sees that marker, aborts (exit 2) if HOME or `ASTRO_HOME` is outside the temporary directory, and otherwise keeps the home its parent made: it never clears or replaces it. A helper that writes the config calls `testenv.RequireTemp(config.HomeConfigFile)` first.

**Coverage.** `internal/archlint` fails a test package, in the root module or any module of its own, with no `TestMain` that calls `testenv.Main` or `testenv.Isolate`. A root package must call the root's `pkg/testing/testenv`; a `pkg/*` module's package calls `pkg/testenv`, and one whose test binary links `pkg/secrets` (`secrets`, `secretstest`, `scaffold`) must pass `testenv.Options{MockKeyring: secrets.MockKeyringForTests, KeyringRefusals: secrets.OSKeyringRefusals}`, or its tests could reach the OS keychain or fall back on its refusal unseen. `e2e` passes `KeepHome: true`, because its harness reads the real docker config and uv cache on purpose and gives every command a home of its own. `pkg/testenv` is a sibling module like the others: each `pkg/*` module that has tests requires it (`v0.0.0-00010101000000-000000000000`, the placeholder version the other sibling requires use) with `replace => ../testenv`, as the root does, and a consumer that builds `pkg/*` modules from source (Astro Desktop) needs one more `replace` line for it. No non-test file of any `pkg/*` module imports it; the shipped binary links it only through `config/config_test_utils.go`, which registers the hook that recomputes the home paths. In `e2e`, every project is also stamped keyring-unavailable (`stampKeyringUnavailable`), so no CLI run reaches the keychain for a login; a case that must use the real one calls `useRealKeychain`, which skips unless the person running the suite set `ASTRO_E2E_KEYCHAIN=1`.

**Using a real resource anyway.** A unit test cannot, by design: there is no switch, and a test that reaches the real home or keychain fails. Changing that means changing the guard (`refuseInTests` in `pkg/secrets`, or `Isolate`) in a reviewed change that says why. An integration test that needs the machine belongs in `e2e`, behind a tier and an opt-in like `ASTRO_E2E_KEYCHAIN`.

## Which Astro Workspace a run acts on

`astrosession.Resolve` (`internal/astrosession/target.go`) decides it, once, for every Astro command; nothing else reads the saved context for a Workspace or checks one for emptiness. The first source that names one wins:

1. the flag: `--workspace` (`--deployment` for a Deployment);
2. the project link, `[tool.astro]` in `pyproject.toml`, for the command families that follow the project: `astro env` and `astro deployment` (`followProjectPreRun` records it on the command's context, `withProjectFollow`; `workspaceTarget` in `cmd/astro` reads it);
3. the claims of the run's API token: a Workspace or Deployment token names its Workspace, a Deployment token its Deployment (`astrosession.TokenIdentity` reads them from the token). An Organization token names neither;
4. the Workspace the saved interactive login last used. Never under `ASTRO_API_TOKEN`, which reads neither the saved login's Workspace nor its host.

### A Workspace the token is not for is refused

The first two sources win before the token's claim is looked at, so on their own they would let `ASTRO_API_TOKEN=<Workspace token for A> astro … --workspace B` target B and fail at the API with a 403. When the run holds a Workspace or Deployment token (a `workspaceId` claim) and `--workspace` or the project's link names a different Workspace, it is refused before any request with `astrosession.WorkspaceDisagreeError`, naming both and where each came from: `ASTRO_API_TOKEN is a Workspace token for A, but --workspace names B: drop --workspace, or use a token for B` (`the project's link names B`, `the request path names B`; a Deployment token reads `a Deployment token for Workspace A`). It is a usage error (exit 2, kind `usage`) marked `OmitsHelpPointer`, like `TargetsDisagreeError`: the message says what to change, and `--help` would not. A flag that matches the claim wins over a project link that does not, as the flag always wins. An Organization token has no claim to disagree with, and a run with no token has none either.

The refusal is for a read that would be made. `astro local start` with a project linked to Workspace B, under a token for A, is refused only when a `source = "workspace"` name has no local value: a value from the project's `.env`, the vault or the shell wins first, so the Workspace is never asked, nothing is sent, and the start proceeds. That is intended, not a gap in the check. When the only reads left are the Workspace's undeclared values, the start goes on without them and, in text mode, prints one stderr note that the Workspace's values were not read and why, naming both Workspaces as the refusal does (`plan.Built.WorkspaceRefusal`, printed by `noteWorkspaceRefused`; never under `-o json`).

Every family reaches the check, by the reader it uses. `Target.Require` returns it first, so each command that resolves through `Resolve` and calls `Require` gets it; a caller that reads `Target.Workspace` without `Require` calls `Target.Disagrees`. A reader with no `Target` calls `astrosession.CheckWorkspace(named, source)`: the core tree's manifest link (`emenv.WorkspaceFor`, which `astro local env list` and `get` call before they read; the Environment Manager provider itself, which declines a read for a Workspace the token is not for, sends nothing and reports `Refusal`, which `plan.Build` returns only when a Workspace value was actually asked for, so an `astro local start` that needs none is not stopped; `instancelocate`'s `DeploymentID` for `astro af -d <name>`; and `astro link add`'s Deployment list), `astro env`'s own `--workspace` (`envScope`), `astro deploy` and `astro deploy bundle`'s `--workspace`, and a Workspace id written in an `astro api cloud` path (`SourcePath`: `/workspaces/<id>`). A caller that wraps a Workspace failure in what it was looking for leaves this one alone (`wrapWorkspaceErr`): it already says what to change.

### Saying where the Workspace came from

`Target.WorkspaceSource` and `DeploymentSource` are the one record of where each answer came from, and three things read them rather than recompute them:

- **A note** on stderr, in text mode only and never under `-o json`, when the source is a surprise: the project link chose a different Workspace than the context would have (`projectNote` in `cmd/astro/project_scope.go`, run by the `astro env` and `astro deployment` pre-run: `using workspace Example from pyproject.toml`), or a token run took its Workspace from the token's claim (`noteTokenWorkspace`, said once by `workspaceTarget` when the command resolves and uses its Workspace, after its arguments are validated: `using workspace <id> from ASTRO_API_TOKEN`). A command that never resolves a Workspace says nothing. There is none when the flag named it, or when the project link named what the context or the token already had.
- **Errors about the Workspace** name it with its source: `no Deployment named "etl" in workspace B (from --workspace)`, `(from the project link)`, `(from ASTRO_API_TOKEN)`. The code that builds a not-found, no-access or nothing-in-it error knows the Workspace's id and where the run took it from, and puts both in a typed error, so the message has the source because it was built that way and nothing rewrites it afterwards. `deployment.NotFoundError`, `NameError`, `NoDeploymentsError` and `NoneEligibleError`, and `instancelocate.DeploymentNameError`, carry `Workspace` and `Source` fields; `astrosession.WorkspaceError` is the general carrier (`Workspace`, `Source`, the words before and after, and the cause it unwraps to), used where there was no error type of the command's own (a listing the control plane refused, a Deployment token's Deployment missing from its Workspace). The platform packages take a Workspace id, so the source reaches them on the client: `deployment.WithWorkspaceSource(client, ws, src)`, which the command layer applies where it resolved the Workspace (`deploymentWorkspace`, `coalesceTarget`, the deploy pickers). A lookup in a different Workspace than the one the client was told about gets no source. The core tree and `astro api` pass the source they already hold (`instancelocate`, from the source `workspace` returns). Each error unwraps to its cause, so its `-o json` kind and code do not depend on the words. A source a person would not expect to be told (the saved login) is not named. Only the lookups above carry it: `astro env` puts it on `env.Scope`, so the scope mismatch (`variable X belongs to deployment D, not workspace W (from --workspace)`) names it, while the owner it reports is the object's own and is not labeled; commands that resolve a Workspace and call the API with the bare client (the `workspace` and token commands) word their errors as the API does.
- **One debug log line** per resolution, through `pkg/logger` at debug verbosity: `workspace X (--workspace), deployment Y (ASTRO_API_TOKEN)`, `none (no source)` for what nothing named.

### `deployment token add` looks in the Deployment's Workspace

A Workspace token can hold a role only on Deployments of its own Workspace, so a Workspace token given to `astro deployment token add` (and `workspace-token add`, which no longer needs a Workspace of the run's own) by `--name`, or picked, is looked for in the Deployment's own Workspace, not the one the command line, the project or the context points at. `tokenSearchWorkspace` in `cmd/astro/deployment_token.go` reads the Deployment by ID for it (one GET, only when no token ID was given and no `--workspace`). `--workspace` stays as the explicit override, and under `ASTRO_API_TOKEN` it is held to the token's Workspace like any other. A Deployment that cannot be read leaves the search to the Organization's tokens, and the error says so and that `--workspace` names one.

### A run with `ASTRO_API_TOKEN` is the token, in both trees

With `ASTRO_API_TOKEN` set, a run uses the token and nothing from the saved login or the saved context: not its access token, not its organization, not its Workspace, not its host. The credential, the organization (`organizationId`), the Workspace (`workspaceId`) and the Deployment (`deploymentId`) come from the token's claims, or from what the command line or the project link names. This holds for every command, in both trees, by one rule in `internal/astrosession` (`token.go`):

- **The platform tree** applies the token to the current context for the process, in the root pre-run (`cmd/astro/setup.go`), and every reader of the context then reads the token's.
- **The core tree** (`astro local`, `astro af`, and the Deployment lookups they make) has no such hook, so `astrosession.TokenIdentity` reads the same claims from the token each time: `Bearer`, `BearerFor` and `Login` return the token (and, for `Login`, its organization and Workspace) instead of a stored login, `Resolve` takes the Workspace from the claim without reading any context, and `instancelocate.Organization` returns the claimed organization. The platform tree's setup (`checkAPIToken`) takes the same claims from `TokenIdentity` before it applies them to the context, so the two trees parse and validate a token in one place. `internal/emenv` reads Environment Manager, and `internal/instancelocate` looks a Deployment up by id or by name, through those, so they send the token under the token's organization.

The Environment Manager read of `astro local env` and `astro local start` follows the same rule (`emenv.WorkspaceID`): the Workspace is the manifest's `workspace`, else, under a Workspace or Deployment token, the token's own. An Organization token names none, so with no manifest `workspace` the read is refused (`workspace (unavailable: the manifest sets no workspace key...)`) and nothing is sent; the saved login's last Workspace is never used.

The host is chosen the same way everywhere, by one function, `astrosession.TokenHost`: the domain the command names on its command line, else the project manifest's `[tool.astro] domain`, else `ASTRO_DOMAIN`, else `astronomer.io`. The saved context is not in the list, so a machine whose current context is dev still sends a token to `astronomer.io` unless the manifest or `ASTRO_DOMAIN` says otherwise. The Deployment lookups of `astro local` and `astro af` (`instancelocate`), the Environment Manager reads (`emenv.WorkspaceOf`) and the platform tree's setup (`environmentDomain` in `cmd/astro/setup.go`, which makes that host the process's current one through the environment login) all take it from there. The environment login stands in for the host's context in memory (`Context.ContextExists`), so setup reads no saved context and saves none, and `config.GetCurrentDomain` is token-aware: once the login is held it is the login's host (`astro context list` and `astro context switch` need no login, so they still show and move the saved pointer). Setup reads the manifest's domain leniently, since it runs for every command (`manifestDomain` in `cmd/astro/token_domain.go`): when the `pyproject.toml` around the working directory parses as TOML, its `[tool.astro] domain` is taken even if another key fails validation, so a command that is no project's still works there, and the commands that load the manifest report its problems themselves. A host is never guessed: a `pyproject.toml` that was found but does not parse stops the run before any request, naming the file, because the manifest's domain outranks `ASTRO_DOMAIN` and the unreadable file might name one. With no `pyproject.toml` at all, or none naming a domain, the host is `ASTRO_DOMAIN`'s, else the default. A selection written under a token (`workspace switch`, `organization switch`) on a host with no saved context is not saved, and says so on stderr (`config.setContextField`). `Resolve` applies the token's claims on that host, with no comparison against the saved context's.

A token that is malformed, expired or has no permissions fails the run, in either tree, with the same sentences and the same `unauthenticated` kind (`ErrAPITokenMalformed`, `ErrAPITokenExpired`, `ErrNotAPIToken`; all match `ErrInvalidToken`), and the run does not read the saved login in its place. `astro local env list` shows a workspace-source name as `workspace (unavailable: unusable ASTRO_API_TOKEN)`, and says why when something needs the value. A token that names no organization is `ErrTokenNoOrganization`. Without a token nothing changes: the saved login, refreshed when stale, is used as before.

A `Target` records the source of each answer. A run that found none gets its error from `Target.Missing`, worded for the token's own kind (an Organization token, or a Deployment token with no `workspaceId`) and by the ways the command takes a Workspace (`Request.Advice`, a `WorkspaceAdvice` bitset: `ByFlag`, `ByProject`, `ByID`, `ByPath`, `ByDeployment`). It only picks the advice, never the Workspace, and the sentence is built from every way set (`so pass --workspace, run it in a project linked to a Workspace, or give the token's ID`), so it never offers a way the command would not take and never drops one it would. A command that asks a question or calls the API calls `Require` first. A Deployment given by ID is identified by it and needs no Workspace (`deploymentWorkspace` in `cmd/astro`): when none is found, which is an Organization token's run and also a saved login whose current Workspace is empty, it is fetched by ID, and the command works in the Workspace it is in. That is one GET: `deploymentWorkspace` returns a client wrapped with the fetched Deployment (`deployment.WithFetched`), and `deployment.GetDeployment` answers from it for that Deployment in its Workspace instead of listing the Workspace and fetching again. A name, a pick, and a value that is not an ID still need a Workspace. `Resolve` reads a token's Deployment only for a caller that sets `WantDeployment`.

## Output

The output contract covers the whole CLI, and lives in [`cmd/cliout`](../cmd/cliout): the `--output` flag, `Renderer.Emit` and its stream twin `Renderer.EmitEvent` (the single door every payload leaves by, so a test can watch what a command publishes), and `cliout.Execute`, which runs the root and reports every failure. Formats are `text` (the default) and `json`; a command offers another only for a special use.

`cliout` is the one place `-o/--output` is registered and parsed: `cliout.AddOutputFlag(cmd, &v)` registers it, with the help `Output format: text or json`, and binds it to `v`, a `cliout.Format`. The flag validates its own value: an unknown one is refused while cobra parses flags, before any pre-run refreshes a token or records telemetry, with `unknown output format "x" (supported: text, json)` as a usage error. So `v` only ever holds a format the command offers, and the command reads it as it is: `cliout.Renderer{Format: v, Out: out}`, with nothing to parse and no error to handle. A command with more to say about a refused value gives it to `cliout.OnBadFormat`, after `AddOutputFlag` on the same command (`astro env list` explains why it has no dotenv). A payload that costs something to build and that the text does not read is handed to `Emit` as a `cliout.Lazy`, which is built only in json mode. A command that offers a format beyond those two declares it as an extra, once, where it registers the flag: `astro env variable list`, `get` and `export` take `dotenv` (`AddOutputFlag(cmd, &v, formatDotenv)`), and `astro deployment inspect` takes `yaml`. The extra shows in the help (`text, json or dotenv`) and in the error's list, and nowhere else. A renderer below `cmd/` may not import `cmd/`, so it takes the command's `cliout.Renderer` as an `output.Emitter` (`Emit(v, text)`): the `pkg/output` lists and `internal/platform/astro/env`'s writers draw only the text and hand the value to it, so their json is the same encoder's. Those packages render; they neither parse nor encode json. `astro deployment inspect` hands its Renderer to `inspect.Print` the same way, with the YAML as its text, so `-o yaml` reaches the Renderer as text. The one format beyond the two they have is `dotenv`, which the command writes itself with `env.WriteVarDotenv`. So a Renderer only ever sees text or json, and `Emit` panics on anything else: a Format that did not come through the flag (`""`, or a value no command offers) is a programming error, not a quiet text rendering. One exception remains: `astro deploy`'s `--output`, which has no `-o`, is a plain string flag because outside a pyproject.toml project it is ignored, and is checked with `cliout.ParseFormat` in `cmd/astro/deploy.go`, only inside one.

Every command in the core tree (`cmd/local`) supports `--output json`: `astro local *`, `astro init`, the root aliases `astro start`/`stop`/`logs`, `astro af`, `astro use`, `astro link` and `astro package`. `TestTreeInvariants` in `cmd/local` fails on a runnable command that lacks it. The rest of the CLI is converging on the same rule: `TestEveryCommandCanReachOutputJSON` in `cmd` fails on a visible, runnable command in any of the trees the tree-wide tests build (see Help, below) that cannot reach an `--output` offering json, except the ones its `lacksOutputFlag` list names for that tree's platform, and that list may only shrink. `astro login`, `logout`, `auth login`, `auth logout` and `otto` are exempt by design, as are the requests the `api` family makes, which print the API's own response and shape it with `--jq` and `--template` (its `ls` and `describe` publish the CLI's own listing and schemas, and take `-o` like every other command). A list is one object with the list under a named key, `{"dags":[...]}`, and `[]` when empty, so a script reads it with one parse and fields such as a total can be added later. Only streaming surfaces (logs, events, build output, `astro local check`'s findings) emit NDJSON, one object per line; a list is not a stream. A result (and the error object) is pretty-printed and colored when stdout is a terminal and compact on one line when it is piped or redirected, while a stream's records go through `EmitEvent` and are one line always, on a terminal too. `astro af` lists use the key names of the standalone `af` CLI they stand in for (`dags`, `dag_runs`, ...), so its skills work unchanged. Human output is the default rendering of the same data, not a separate code path.

### Logging

The diagnostic log is separate from output: it goes to stderr, and nothing parses it. There is one log, in [`pkg/logger`](../pkg/logger/logger.go), built on `log/slog`. Its handler is installed as slog's default, so a line reaches the same level and the same place whichever way it is written: `logger.Debugf` and its siblings in the root module, `slog.Debug` in the `pkg/*` sub-modules (which cannot import the root module, and need no dependency for slog), and a stray standard-`log` call, which slog's default carries at info. New code in a sub-module logs with `log/slog`; nothing else configures a logger or a level.

A warning is not a log line. Something the person running the command needs to know (a deprecation, a value the CLI changed for them, a step it skipped) is written with `cliout.Warn` (or `ansi.Warn` below `cmd/`) to the command's stderr, and always prints: `--verbosity error` must not hide that a `--page-size` was cut to 100. The log is for detail that matters when something goes wrong, and `--verbosity` decides whether it prints, so it is written at debug. A log line above debug belongs only where nobody reads the command's stderr: the proxy daemon, whose log is a file, and otto, whose full-screen UI sends the CLI's log to one. `forbidigo` (`.golangci.yml`) fails a call that logs at info, warn or error anywhere else, in every module: `logger.Infof`/`Warnf`, `slog.Info`/`Warn`/`Error` and their methods on a `*slog.Logger`, and the standard `log.Print` family. Code that does run where nobody reads its stderr says so at the call, `//nolint:forbidigo // <why>`; `nolintlint` requires the why and fails the comment once nothing on its line needs it. Every warning is led by the same yellow `Warning:` (`ansi.WarningLabel`), which the helpers add: a message never spells a label itself. The text after it starts in lower case unless it starts with a name, says what happened and then what the CLI did or what to do (`could not detect the Airflow version (…); using 3.1.2. Pass --airflow-version to choose one`), puts an error in parentheses or after a colon, and, if it is one sentence, has no closing period. `WARNING:` (`ansi.DangerLabel`) is a different thing: it leads the confirmation of something that cannot be undone.

The level is set once per run by the root's pre-run (`SetupLogging`, [`cmd/logging.go`](../cmd/logging.go)), on every command, including those that skip the rest of the pre-run (`astro local`, the proxy daemon), because setting it up reads no network and writes nothing. The level is the first of these that is set: `--verbosity`, `ASTRO_VERBOSITY` (which the proxy daemon `astro local start` spawns inherits), the `verbosity` setting, and otherwise `warn`. The levels are `debug`, `info`, `warn` and `error`, and 1.x's other names still parse (`warning`, `trace`, and `fatal` and `panic`, which log nothing). A bad `--verbosity` is a usage error; a bad value in the environment or the setting is reported as a warning and passed over.

A line reads `Debug: running cmd="docker compose up -d" env=DOCKER_HOST`: the CLI's label for the level (`Warning:` as a warning has everywhere), the message, then key=value attributes. The time leads the line when the log goes to a file rather than a terminal (the proxy daemon's log, otto's). Messages and values are printed without escape sequences or control characters (`pkg/input`), because a line can carry text from an API or a container. What a debug line may hold: a command line, a path, a status; never a secret. The local engines log the environment they add to a command by name only, uv's command lines have a URL's credentials masked, and a health wait logs when the answer changes rather than every poll.

### Adding `--output` to a command

The commands in `lacksOutputFlag` gain `-o json` a family at a time (`deployment variable`, then `deployment token`, and so on), some before the 2.0 release and some after. A conversion must not break anyone, so each one follows three rules.

1. **Text mode does not change.** The same stdout, the same wording, the same exit codes (with the one exception rule 3 describes). JSON is the new path. Under `-o json`, stdout holds the payload and nothing else: progress, warnings and notes go to stderr (`env_link.go`'s `deploymentPickupNote` is one).
2. **A new JSON shape is free; changing it later is breaking.** So design it once. Keys are snake_case. A list is an array under a named key (`{"tokens":[...]}`), `[]` when empty, never `null`, never a bare top-level array, never NDJSON. A create or update returns the object as it now is, not a confirmation sentence. The shape is pinned once, by a schema golden: add each type the command publishes to its tree's `publishedPayloads` (`cmd/local/schema_cases_test.go`, `cmd/astro/schema_test.go`, `cmd/apc/schema_test.go` for the APC (Houston) platform, `cmd/schema_test.go` for the commands the root builds itself: `version`, `context`, `config`, `telemetry`, `auth token`, and `cmd/api/schema_test.go` for `astro api … describe -o json`), run `make update-schemas`, and read the file it writes. A type that reaches `Emit` with no golden fails the package's run, as does a key in a golden that is not snake_case: every tree arms the same watch (`cliouttest.Watch`) in its `TestMain` and runs the same key check (`cliouttest.KeyProblems`), and a tree that pins shapes keeps a `minWatchedPayloads` floor above 0. The command's own tests then decode what it printed and assert what it means: the exit code, what happened to each input, what a list holds, `[]` when it is empty. They do not restate the shape, and in text mode they check that the messages and rows are there, not how a table pads them. Text is pinned byte for byte only where something parses it, as deploy-action parses `astro deployment inspect`.
3. **A command that exits 0 after failing is a bug.** Fixing it is a bug fix, not a breaking change. It still goes under the PR's `## Breaking changes`, so the release notes say that a script which used to see 0 will now see 1.

The work itself:

- Register the flag with `cliout.AddOutputFlag`, bound to a `cliout.Format` the command reads as it is, and publish through `cliout.Renderer.Emit`, with the text renderer printing exactly what the command printed before.
- Write the text renderer with [`cmd/cliout/text.go`](../cmd/cliout/text.go), which is the standard library and nothing else. `cliout.Text` (or `cliout.WriteText` outside `Emit`) hands the renderer a `bufio.Writer`: its error is sticky, so the renderer writes its lines unchecked and the one error comes back at the flush, instead of every `Fprintln` wrapped in `if _, err := ...`. A list is a `cliout.Table` (a header, rows, and the message for no rows), which lays its columns out with `text/tabwriter` the way the CLI's tables always looked: `r.Emit(v, cliout.Text(table.Render))`. It is `pkg/texttable.Table` under another name, so code below `cmd/` draws the same table. `pkg/printutil.Table` is the old way; its uses move over a family at a time. `deployment variable`, `deployment token` and `astro af config` are the examples to copy.
- Move the command toward the core. The platform function returns a result (what happened to each input, the object afterwards) instead of printing it, and `cmd/` renders it in either format. `astro deployment variable create` does this, and is the one to copy: `VariableModify` returns one outcome per input plus the variables afterwards, and `cmd/astro/deployment_variable_render.go` is the only place deciding how any of it looks.
- Delete the command's entries from `lacksOutputFlag`. `TestOutputFlagAllowlistOnlyShrinks` fails on an entry left behind for a command that now has the flag. Nothing is ever added to the list.
- If the command asks anything, check that each prompt names the flag that answers it (`input.AnsweredBy("--yes")`). Under `-o json` the prompt is refused as `input_required`, and without the flag named the message can only say "pass the answer as a flag". See [Prompts](#prompts).

Failures need no work of their own: once the command has `--output`, `cliout.Execute` reports them as below.

The property as a whole is checked end to end, against the built binary: `TestEveryCommandWritesOnlyJSONToStdout` in `e2e/` walks every command the binary has (through `astro __complete` and each command's `--help`), runs each with `--output json` logged out, logged in to an Astro or an APC API that refuses connections, and inside a project, and fails on anything on stdout that is not the one result, the stream's lines, or the one error object, on an error on stderr as well, and on a group run bare that is not a usage error. A new command is run with no change to the test; one it must not run, or that has no `--output json` by design, is listed there with the reason.

### Failures

Under `--output json`, a command that fails writes one object on stdout, and no error on stderr: `{"error": ..., "code": 1, "kind": ...}`. Warnings may still be on stderr, as on a success, such as a deprecation warning (see [Deprecated spellings](#deprecated-spellings)); stdout holds exactly one document either way. This holds for every command whose `--output` is `json`, whichever tree it is in, and for every way it can fail: in its run, in a pre-run (no login), or before either, on a flag or argument cobra rejects. `code` is the exit status the process ends with. `error` is prose for a person and may be reworded. `kind` is the stable name for which failure it is, and is contract: a consumer branches on it instead of matching a sentence. It is snake_case, the same vocabulary as a check finding's `kind` (`import_error`, `duplicate_dag_id`). A command with no `--output`, or in text mode, prints `Error: ...` on stderr and never its usage block: `cliout.Execute` turns cobra's automatic usage off for every command. A runtime failure is the error alone. A usage error is followed by a pointer to the failing command's help, `Run astro deployment list --help for usage.`, and an unknown long flag that one of the command's visible flags is clearly closest to (within the root's suggestion distance, two by default, counting two swapped neighbors as one edit, or a prefix of it; held to fewer edits than half the typed name's length, one at the least; and no other as close. Subcommand suggestions keep cobra's own matcher, where a swap is two edits) gets `Did you mean --workspace?` between the two. A usage error found before the command ran (a flag, the argument count, a missing required flag, an unknown subcommand) always gets the pointer. One the command returns itself does too, unless it was marked `cliout.UsageNoHelp(err)` (below). A declined confirmation (`Error: aborted`) and an interrupt (`Error: interrupted`) are not usage errors and print the error alone.

Some failures publish something else instead, and a consumer has to expect them (neither adds a second object):

- a command that already wrote a richer structured payload (`cliout.JSONShown`): a start blocked on missing env values publishes that list;
- a command that carries its own exit code (`cliout.ExitError`): `astro local check` publishes its NDJSON summary, `astro af runs trigger-wait`, `astro af runs wait` and `astro af tasks wait` their result, and `astro local run` exits with the child's code.

#### Marking a usage error, and opting out of the help pointer

A command returns a usage error it finds once it runs with `cliout.Usage(err)`: a flag it cannot run without whatever the terminal (`errRequiredFlag` in `cmd/astro` for a missing `--deployment`; a check cobra's `MarkFlagRequired` cannot say, such as one of two flags), a flag refused with another, a value it does not accept. It exits 2, publishes kind `usage`, and gets the pointer to the command's help. A package below `cmd/` that cannot import `cliout` marks its error with an `IsUsageError() bool` method instead (`usageerr.Usage` from `internal/usageerr`, a package of only the marks that any package can import; `NameError`). A value the command could ask for at a prompt is not a usage error: that is `input_required`, which is how `pkg/input` answers it when nothing can be asked.

The pointer is decided by the error alone. A command's `SilenceUsage` decides nothing: cobra's usage block is kept out by the root, because `cliout.Execute` turns `SilenceUsage` on for the root for the length of the run, and cobra prints the block only when neither the failing command nor the root silences it. So commands do not set `SilenceUsage`, and a root that sets it itself turns the pointer off for the whole tree.

`cliout.UsageNoHelp(err)` is the explicit opt-out: a usage error, exit 2 and kind `usage` as before, with no pointer. Use it when the message already says what to run instead, so the command's help would settle nothing and the pointer would bury the answer. A package that cannot import `cliout` gives its error an `OmitsHelpPointer() bool` method that returns true (`usageerr.NoHelp`, `NameError`). It applies only to an error the command returns once it runs: one found before the command ran (a flag, the argument count, a missing required flag, an unknown subcommand) always gets the pointer. It is used by:

- every removed command and removed alias stub, in `cliout.RemovedCommand` itself, since the message names the replacement;
- a removed or unknown `astro config` setting, which names the setting or `astro config list`;
- `astro local` and `astro local af` given a verb that moved, which name the command to use;
- a verb that does not fit a token (`astro workspace token delete` of a broader token, and the token errors that name `add` or `remove`), which names the verb that does;
- a Deployment name several Deployments share, or none does (`NameError`), which lists the ids.

### The root pre-run fails closed

The root's pre-run (`CreateRootPersistentPreRunE` in `cmd/root_hooks.go`) runs Astro's setup (`cmd/astro/setup.go`: the `ASTRO_API_TOKEN` check, the saved login, a renewal of its access token) before a cloud command. It **propagates the error setup returns**, as it was returned, so the message, the `kind` and the exit status reach the person; a command that cannot be sure whose credentials it runs with does not run. It swallows nothing by substring. What is soft is decided inside setup, with typed errors, and never reaches the hook as an error:

- the version check (`version.CompareVersions`), logged at debug level;
- a renewal of the access token that fails (the identity provider is unreachable or refuses the refresh token, or the config will not take the tenant or the renewed login) while the current access token is inside the refresh margin but **not yet expired**: logged at debug level, and the command runs on the token it has. Past expiry the same failure is hard. If the provider answered and the renewal could not be saved, the old refresh token may be retired: the run warns once on stderr, naming the config file, and does not present that refresh token again for the rest of the run (`errRenewalRetired`); the next run, with the token expired, asks for a login. The renewed login is saved in one config write (`Context.SetSharedLogin`), not one per field. A provider that answers 5xx or 429 says nothing about the refresh token (`httputil.TransientStatusError`, a transport error): no browser login is offered. Every renewal, the 401 path (`RefreshLogin`) too, runs under the cross-process lock `FreshLogin` takes, re-reading the login once it holds it, so commands that find the same token stale renew it once; a login whose access token still works waits for that lock one `fsatomic.LockTimeout` only and carries on without renewing.

Everything else stops the command: a token in `ASTRO_API_TOKEN` that is malformed, expired or has no permissions (`ErrAPITokenMalformed`, `ErrAPITokenExpired`, `ErrNotAPIToken`), a token that cannot be applied to the run (the environment overlay), an organization lookup that failed, a saved login that needs a browser the run may not open (`auth.ErrLoginNeeded`), an expired login that could not be renewed (`ErrLoginRenewal`), no context or a home config that did not parse (`ErrConfigUnreadable`, which names the file), a failed device login, and an interrupt (`input.ErrInterrupted`, exit 130). A run with `ASTRO_API_TOKEN` set, in either tree, uses the token's credential and organization, and for its Workspace and Deployment the flag, the project's manifest or link, or the token's claims, in that order (see [Which Astro Workspace a run acts on](#which-astro-workspace-a-run-acts-on)). It never uses the saved login or the saved context: not its access token, its organization or its Workspace. The platform tree gets this from the setup's overlay, which takes its claims from `astrosession.TokenIdentity`; the core tree (`astro local`, `astro af`) skips the root's pre-run and reads the same identity directly.

Commands that need no login are not affected: those with `NoLoginAnnotation`, `login`, `logout`, `version`, `help`, `config`, `context`, `telemetry`, the removed-command stubs and `completion` skip setup as before, and so do the core tree (`astro local`, `astro af`) and Astro Private Cloud, which have no Astro setup in the hook.

A command the pre-run stops is still recorded: `telemetry.TrackSetupFailure` sends one `CLI Command Setup Failed` event with the command, the kind of the error (`error_kind`) and the usual properties, anonymously, and nothing from the message or the credentials. The command's own event is not sent.

**Shell completion skips the whole pre-run**: cobra's `__complete` and `__completeNoDesc` requests (and the `completion` script generators) run no version check and no setup. Completion runs on every TAB, so it makes no network call, starts no login and prints no prompt, logged out or offline. Its candidates come from the command tree; a completion that needed the API would offer nothing rather than log in.

### Commands in messages

The CLI writes a command, flag, path or key in its own output as plain text, with no backticks: "astro dev start was removed in Astro CLI v2. Use astro local start instead." That holds for errors, warnings, notes, prompts, next steps and help. A terminal prints a backtick as it is, and a script or Astro Desktop reading an error object's `error` or a payload's notes gets it as it is, so markdown in a message is noise wherever it lands. Where a bare command reads ambiguously mid-sentence, the sentence is rephrased ("The set command creates ...", "then use astro local start --docker") rather than quoting it. These docs are markdown and keep their backticks.

Two tests hold the rule. `TestMessagesWriteCommandsAsPlainText` in [`internal/archlint`](../internal/archlint/backticks_test.go) parses every tracked non-test Go file in the repo, sub-modules included, and fails on a string literal holding a backtick. Its `backtickAllowed` list names what may hold one because it is markdown or code where the backtick means something: the AGENTS.md `astro init` writes, the upgrade prompt handed to Otto (the CLI's own words in it included), and one shell-metacharacter set. An entry no longer needed fails the test too. `TestHelpHasNoBackticks` in `cmd` renders every help page in every tree, hidden commands included, and fails on a backtick, which also catches text assembled at run time. It reads every flag's usage string as well, since pflag strips a backticked word out of the rendered help and uses it as the flag's value name. Text the CLI passes through from uv, Airflow or an API is printed as it came.

### Prompts

Whether a run may ask a question is decided once, by one rule, and every prompt and picker follows it. A question needs a person at a terminal: stdin to answer on and stderr to see the question on.

**Non-interactive.** A run is non-interactive when any of these holds:

- `--output json`;
- stdin is not a terminal, or stderr is not a terminal (`input.StdinIsTerminal`, `input.StderrIsTerminal`, the plain console check a hidden prompt needs; a Cygwin or MSYS pty such as mintty is not one);
- the `CI` environment variable is set to a truthy value (anything but empty, `0` or `false`, in any case, surrounding spaces ignored), or a CI system that does not set `CI` says so (`JENKINS_URL` or `HUDSON_URL` set and not empty, or a truthy `TF_BUILD` for Azure Pipelines; found by the list telemetry uses, `telemetry.IsCISystemSet`);
- the global `--non-interactive` flag is passed. It is declared once, persistent, on the root, so every command at every depth takes it, a removed command's stub included (a stub parses no flags and asks nothing).

In a non-interactive run every prompt and picker is refused before it writes or reads anything, as kind `input_required`. The failure names what was asked and the flag or argument that answers it (`--yes`, `--deployment`, `--name`, "the user's email as an argument"), and says why it could not ask: "with --output json it cannot", "stdin is not a terminal", "stderr is not a terminal", "with CI set it cannot", "with --non-interactive it cannot". A command with no such flag says to pass the answer as a flag. `--non-interactive=false` asks again even with `CI` set, for debugging a CI job at a terminal. It restores nothing else: not `--output json`, and not a missing terminal.

**An answer is never read from a pipe.** `echo y | astro local reset` is refused like any run with no terminal: a script passes `--yes` or the flag that answers. That keeps a piped payload from being taken for an answer, and keeps a password from being echoed by whatever types at the far end (ssh without `-t`, `docker exec -i`). A hidden prompt (`input.Password`) follows the same rule and needs nothing of its own.

**Payload stdin is not an answer.** A command that reads data from stdin (`--value -`, `--file -`, a value piped to an `astro env` command) reads it as data, and that is not a prompt, so the rule does not touch it. A prompt after it finds stdin is not a terminal and is refused.

**At a terminal** nothing else changes: the question goes to stderr and the answer is read from stdin. Ctrl-D (end of input) with no answer is `input_required`, "input ended with no answer" (not a no, and not an invalid selection); Ctrl-C is `input.ErrInterrupted` (exit 130, with the Windows console grace); a decline is `input.ErrAborted` (kind `aborted`, exit 1).

**Logging in is not asking.** An `astro login` or `astro auth login` the person ran works in a non-interactive run: running it is the consent, so it prints the login link and waits for the browser's callback, within its usual timeout, with no Enter pause and no browser started for it (`auth.LoginCommand`), including with stdin from `/dev/null`. `--login-link` is not refused. A login another command starts because it found none (`auth.Login`) is refused in such a run with `ErrLoginNeeded`, saying to set `ASTRO_API_TOKEN` (`astro login` prints a link for a person to open, and waits for it). A first-run guess that the login is a new account (which opens the sign-up screen and preselects creating an organization) is made only where the run may ask; otherwise only `--signup` says so. A login with no organization that cannot ask whether to create one says to create or join one in the Astro UI or be invited.

stdout carries a command's results only, so a question is never drawn there: the `pkg/input` prompts, the pickers (`pkg/picker`, which every picker is built on), the warning a confirmation shows, and the whole login flow (the welcome, the link, the progress) write to stderr. With stdout redirected to a file the person still sees what they are asked, and the file holds no prompts. The root's pre-run writes its notes and its logs to stderr too. The exception is Astro Private Cloud's `deployment create` and `upgrade` pickers (the namespace and version tables), which still draw on the writer their command hands them, stdout in text mode.

There is one resolver. `cliout.Execute` installs a process-level guard for the run (`pkg/input.SetGuard`, answering from `input.Refusal`), and the guard reads the command's own parsed `--output` and `--non-interactive` when a question comes up. Every prompt consults it:

- the `pkg/input` primitives `Text`, `Confirm`, `ConfirmOrAbort` and `Password` return a `*input.RequiredError` before they write or read anything;
- any prompt that reads its own reader calls `input.MayAsk` first. `pkg/picker` does so for every numbered table a person picks a row of: it is the one picker, so a new one is a `picker.List` with its own `About`, `AnsweredBy` and invalid-selection error, not a table and an `input.Text` of its own.

A command that has to decide whether to prompt or to fail (a picker that fetches rows first, a target that is optional) asks `input.CanAsk()`, never a terminal check of its own. A shared picker cannot know which option answers it (a user is an email argument to one command and a flag to another), so the command says so before it asks (`input.HintAnswer`, from `mayPick` in `cmd/astro`) and every refusal about that question names it; the hints are cleared when the run ends. A call site passes `input.AnsweredBy("--yes")` to name its flag, and `input.About("a workspace")` when its prompt text is a bare `> `. The guard is process-level rather than a context value because the shell platform packages ask from call chains that carry no context.

Every confirmation is `input.Confirmation` (`ConfirmOrAbort` is it, on stdin and stderr; `astro local` runs it on its own streams with `[y/N]` for the choices), so they all behave alike: the question is written, input that ended or Ctrl-C closes its line before the error, the answer is decided on its `input.Plain` text, and input that is nothing but escapes is no answer. `input.Plain` drops escape sequences, control characters and the characters that hide in text or reorder it (the bidirectional controls, the zero-width space, the byte order mark), and keeps the zero-width joiner and non-joiner, which emoji and Persian and Indic words need. A question that embeds a path from the machine (`astro local reset` names the project's) cleans that path with `input.Clean`, which removes the same characters but changes nothing else, so a directory named with an escape cannot write to the terminal and two sibling directories that differ in their spacing are still named apart. A refusal that names a question quotes it with `input.Quote`, not `%q`, so a Windows path in it keeps single backslashes.

A command that refuses in its own words marks the refusal with `input.Required(err)`, so it keeps its words and gains the kind: `astro deploy` with no target, a link picker with no NAME, and a deployment several links make ambiguous.

Tests: a test binary counts stdin and stderr as terminals (`testing.Testing()`), since a test's stdin is a pipe and its stderr a file; a test of the rule itself turns that off with `input.SetTerminals(false, true)`.

Ctrl-C at a question ends it at once. The first interrupt of a run cancels the run's context rather than killing the process, so a question blocked reading a line from stdin would echo `^C` and go on waiting until a second Ctrl-C or an Enter. `cliout.Execute` hands the run's context to `pkg/input` too (`input.SetInterrupt`, beside the guard), and every question `pkg/input`, `pkg/picker` and the shared confirmation (`input.Confirmation`) ask readss its line through `input.ReadLine`, which returns `input.ErrInterrupted` as soon as the context is canceled, after ending the prompt's line so the error starts on a fresh one; a question reached after the interrupt is refused before it is printed (`input.MayAsk`). The login flow's "Press Enter" handles Ctrl-C itself. The run exits 130. A password prompt reads a raw terminal and returns the same error for the Ctrl-C keypress.

The rule for a new prompt is to resolve its context before it asks: find the project, the Airflow or the links it acts on, and check its flags, before the question, and name the concrete target in it rather than "this project". `astro local` and `astro link` follow it: in a directory with no project they fail as `no_project` rather than ask about a project that is not there, and `astro local reset` names the project's path. Nothing checks the rule elsewhere in the CLI.

### Exit codes

| status | meaning |
| --- | --- |
| 0 | success |
| 1 | the command failed, including `input_required`: a question it could not ask. Not 2, because a question can come after work has started, so the "nothing ran" that 2 promises would not hold. The same refusal with no terminal, in CI or with `--non-interactive` exits 1 too. A script that needs to tell it from other failures reads `kind` |
| 2 | usage error: an unknown flag or subcommand, a flag value the command does not accept (`--output yaml` included), the wrong number of arguments, a missing required flag, a group run with no subcommand under `--output json`, whether it has a RunE of its own (`cliout.GroupHelp`) or not (`cliout.Execute` answers it); in text mode it prints its help and exits 0, as before. Nothing ran |
| 130 | interrupted (Ctrl-C or SIGTERM); the command unwound what it had started. The first Ctrl-C at a question ends it at once (`input.ErrInterrupted`) |
| the command's own | `astro local check`: 1 when a check failed, 2 when it could not reach a verdict (no environment, no project). `astro af runs trigger-wait`, `astro af runs wait` and `astro af tasks wait` (and their `astro local af` forms): 1 when the run failed, or for `tasks wait` when the task cannot reach the state, 2 when the wait timed out. `astro local run`: the child's status |

The command-specific 2s predate the usage 2. A script that runs one of those commands tells them apart by what it published: a usage error under `--output json` is an error object with kind `usage`, while `check`, `trigger-wait`, `runs wait` and `tasks wait` publish their own result.

### Kinds

`cmd/local` names the failures of its commands ([`cmd/local/problemkind.go`](../cmd/local/problemkind.go)), the root names the cloud ones ([`cmd/problemkind.go`](../cmd/problemkind.go)), and `cliout` names `usage`, `input_required` and `aborted`, which it tries in that order before any table. The root composes the tables, `cmd/local`'s first, and the first match wins.

| kind | meaning |
| --- | --- |
| `usage` | the command was invoked wrongly; exit status 2 |
| `input_required` | the command needed an answer it would have asked for, and this run could not ask: under `--output json`, with stdin or stderr not a terminal, with `CI` set or `--non-interactive`, or because stdin ended with no answer (Ctrl-D). The message names the flag that answers it, and the question, since a refused question is never written. Exit status 1 (see [Prompts](#prompts)) |
| `aborted` | the command asked for confirmation and was answered no, so it did nothing it was asked to (`input.ErrAborted`, which a declined confirmation returns in `astro local`, the Astro commands, `astro context delete`, and the Astro Private Cloud commands: workspace delete, the service-account deletes, deployment delete, unadopt, hibernate, wake-up, and the dag_deploy question of deployment create and update: `Error: aborted`, and nothing on stdout). Exit status 1: declining is not success. Not 130, which is an interrupt. In a run that cannot ask (the `input_required` row) no confirmation is asked: it is refused as `input_required`, naming the flag that answers it, so `aborted` is an interactive failure |
| `no_project` | no project here: no `pyproject.toml` with `[tool.astro]` |
| `foreign_mode` | the project is running in the other mode |
| `already_running` | the project is already running |
| `health_timeout` | Airflow did not become healthy in time |
| `start_timed_out` | the containers did not finish starting in time, so the start gave up on them; nothing is still coming up (Docker mode) |
| `locked` | another start of this project is in progress; try again (Unix only) |
| `unsupported_base` | the image base is not one this mode can run |
| `database_newer_than_airflow` | the metadata database was migrated by a newer Airflow (Docker mode) |
| `not_running` | nothing is running for this project |
| `deployment_hibernating`, `deployment_deploying`, `deployment_unhealthy`, `airflow_unavailable` | an Astro Deployment's Airflow did not answer (see [instances.md](instances.md#when-a-deployments-airflow-does-not-answer)); `deployment_hibernating` is also `astro deploy` refused because the Deployment is hibernating (see [deploy.md](deploy.md#1-image-deploys) and [Dags-only deploys](deploy.md#2-dags-only-deploys)); `deployment_deploying` and `airflow_unavailable` mean try again |
| `unauthenticated` | no usable Astro login: none was made, the API refused the token (401), one was needed and a run under `--output json` may not start a browser login, the saved login expired and could not be renewed, the home config did not parse (the message names the file), `ASTRO_API_TOKEN` is malformed, expired or has no permissions, or the environment holds both of the retired `ASTRONOMER_KEY_ID` and `ASTRONOMER_KEY_SECRET` and no API token (the message names `ASTRO_API_TOKEN`) |
| `forbidden` | the login lacks the permission this needs (403) |
| `not_found` | the Astro API has no such object (404) |
| `conflict` | the Astro API refused because of the object's current state, such as one that already exists (409) |
| `api_unavailable` | the Astro API failed on its side (5xx), or the organization lookup for `ASTRO_API_TOKEN` got no answer at all (the connection was refused or reset, the host or its name could not be reached, a timeout; not a certificate or TLS failure, a malformed URL or a canceled request); try again |
| `no_deployments` | an Astro command that needed a Deployment picked found none in the workspace, and created none in its place; create one with `astro deployment create` |
| `no_eligible_deployment` | the Astro workspace has Deployments, but none the command can act on, such as `hibernate` and `wake-up` with no development Deployment (or with a Deployment API token scoped to one that is not for development) |

The cloud kinds come from the status on the `*httputil.StatusError` that every Astro API failure is normalized into, and `unauthenticated` also from the "no context" and "not logged in" errors raised before any request. `no_deployments` and `no_eligible_deployment` come from the Astro Deployment selector's own error types (`deployment.NoDeploymentsError`, `deployment.NoneEligibleError`), matched by type, not by status. APC (Houston) failures carry no kind: its client reports them as text.

A failure with no kind publishes no `kind` key rather than an `unknown` catch-all. A kind is added only when the CLI can recognise the failure reliably (a sentinel it wraps, a type it can assert, or a status on one), never for a failure nothing emits. Changing a kind breaks whatever reads it.

### Removed 1.x commands and flags

A script written for Astro CLI 1.x is told what replaced what it typed rather than only that it is unknown. Either way the failure is a usage error: exit 2, and the `usage` error object under `--output json`.

A removed command stays in the tree as a hidden stub that fails naming its replacement: `astro dev` ([`cmd/local/dev.go`](../cmd/local/dev.go)), `astro run`, `astro dbt` (whose `deploy` and `delete` moved to `astro deploy bundle`), `astro deployment airflow-variable|connection|pool`, and `astro env … create|update`. Every stub is built by `cliout.RemovedCommand` ([`cmd/cliout/removed.go`](../cmd/cliout/removed.go)): hidden, with flag parsing off so an old invocation's flags reach it, a `Short` starting `Removed in v2`, and the `removedCommand` annotation. A stub has a pre-run of its own that runs the root's and no group's, so it never reaches the project lookup of `astro deployment` or `astro env`. The root's pre-run reads the annotation. It reads `--verbosity` from the raw arguments, sets up logging and records the command (`telemetry.TrackRemovedCommand`), and runs no login or version check. So a machine that is logged out, or a project that does not parse, is still told what to run. The event is sent only once telemetry is set up, meaning the first-run notice was shown on that machine. A stub never shows the notice itself, because the core tree leaves no state behind. So the counts miss fresh machines and CI runners that start fresh: a count near zero is not on its own a reason to remove a stub. A stub fails with a usage error whose message says `` `astro …` was removed in Astro CLI v2 `` and names the command to use instead, or says there is none. `astro dev` publishes the error object (`cliout.ErrorObject`, embedded) under `--output json`, with its whole mapping of 1.x `dev` commands besides.

[`cmd/testdata/v1_commands.tsv`](../cmd/testdata/v1_commands.tsv) is the inventory of 1.x commands, in the same three trees as the flag inventory below. It also lists every 1.x alias, each as a path that spells the command by that alias (its ancestors by name), so dropping an alias fails the test. Only the tests read it, since a stub needs no inventory to be found. `TestEveryV1CommandStillRunsOrSaysWhatReplacedIt` resolves every path in it against its v2 trees, APC at both ends of its version gates. It passes a path that names a command v2 has, at its own name or a 1.x name kept as an alias, or that reaches a stub, which it then runs, in text and under `--output json`, with every other hook disarmed. Below APC's version gates a path may also reach the stand-in for a command the platform is too old for; in any other tree that fails. It fails on a path that stops at a command with words left over, which is a command dropped without a stub or renamed without an alias. To remove a command, replace it with a stub; to rename one, keep its 1.x name as an alias. To drop a 1.x alias, add the path at that alias to the inventory and a stub in its place with `cliout.RemovedAlias`, which names the command it spelled by its whole path (`cliout.Execute` sets the stub's `Short` in the walk it already makes over the built tree): that is how `astro deployment de` and every other delete's 1.x alias `de` fail, since `de` is also `astro deployment`'s own alias. Every `delete` and `remove` answers to `rm` and to no other alias (`TestDeleteAndRemoveAnswerToRm`), and `TestRemovedAliasStubsNeverRunTheirCommand` runs each such stub on the real trees with its command's runs replaced by a recorder, to check that the stub never runs it. No command answers to a word one of its ancestors answers to, a stub aside (`TestNoCommandAnswersToAWordAnAncestorAnswersTo`). `TestEveryRemovedCommandStubIsA1xCommand` fails on a stub that no 1.x path reaches, and `TestRemovedCommandStubsNeedNoLoginAndAreRecorded` runs stubs on the real tree to check that none reaches the login or the project lookup and that each is recorded.

A removed flag is not registered on any command. Two files in `cmd/` describe it:

- [`cmd/v1_flags.tsv`](../cmd/v1_flags.tsv) is the 1.x inventory, embedded in the binary: every visible flag on every runnable 1.x command, its own and those it inherited, with its shorthand and whether it took a value, and the hidden ones 1.x still accepted as deprecated. It records three 1.x trees: Astro for a non-hosted organization (`astro`), Astro for a hosted one (`astro-hosted`, whose `deployment create` and `update` had flags of their own), and APC (`apc`). It records 1.x, so nothing in v2 changes it.
- `removedFlags` in [`cmd/removed_flags.go`](../cmd/removed_flags.go) is the registry of messages, keyed by flag name.

The root's flag error func (`flagError` in [`cmd/unknown.go`](../cmd/unknown.go)) runs when cobra reports a flag the invoked command does not have. It records the flag in telemetry like any unknown flag. Then, if the inventory says 1.x had that flag (or that shorthand) on that command (at its v2 path, at a 1.x name it keeps as an alias, or at the path of the 1.x command it replaced under another name, which `v1Predecessors` maps: `astro dev start` for `astro local start` and `astro start`) in the tree this machine's scripts were written against (`v1TreeOf`: APC, or Astro hosted or not, read from the context only then), it returns the message of the first registry entry that applies there, as a usage error. This happens while flags parse, so it fails before any pre-run logs in or asks an API anything. A command that still has a flag of that name never gets there. Neither does one 1.x did not have and that replaced none, or had without the flag: `astro local reset -f` gets cobra's own error, because `astro dev kill`, which it replaced, had no `-f`. A shorthand 1.x gave a flag the command still has under its long name alone (`astro local start -p`, `astro deploy -f`) is told that name, with no entry needed. Every refusal starts with the flag as the run typed it (`-s was removed in Astro CLI v2: use --component scheduler`), so an entry gives only the reason that follows. A registry entry can narrow itself further. `needs` limits it to commands that have the replacement (`--json` maps to `-o json` only where there is an `-o`), and `under` limits it to a command and everything below it, for a name whose replacement differs by command (`--template` on `deployment inspect`). Where names overlap, the narrower entry comes first.

A run that asks for help (`-h`, `--help` or `--help=true`) gets the help, not the refusal. A shell asking for completions (`__complete`) gets them: cobra parses flags itself there, without the flag error func, so when a flag typed is one the command being completed does not have, `acceptRemovedFlags` gives that command each removed flag 1.x had on it as a hidden flag, and each shorthand 1.x gave a flag it still has under its long name alone, for that run only. The command completed is the one cobra's own `Find` resolves, so a removed flag typed before a subcommand's name (`astro api airflow --json ls`) completes as cobra would complete it without the tombstones: a run of that line fails too, since the parent never had the flag.

An entry marked `v2Only` is the one exception to that inventory check: it names commands where 1.x did not have the flag, and answers there for a 1.x spelling a script may carry over to a v2 command 1.x did not have (`astro env list --workspace-id` says to use `--workspace`), or for a spelling an earlier v2 build gave a command and took away (`astro deployment team --workspace`). To remove a flag, delete it and add an entry for its name if none applies yet. `TestEveryV1FlagStillWorksOrSaysWhatReplacedIt` runs every inventory flag against its v2 tree, and every flag of a command in `v1Predecessors` against the command that replaced it. It fails on any flag v2 neither has nor reports, checks that each refusal is the message its entry gives there, and fails on an entry that no flag in the inventory reaches. `TestRemovedFlagsSayWhatReplacedThem` needs a case for every entry. The entries go in v3, once the unknown-flag events show nobody still passes them.

### Short options

A short option means exactly one thing, in every tree (Astro, hosted Astro, APC, the root and `astro local`), except on the API passthrough commands (below). The table is `utils.ShortOptions` in [`cmd/utils/shorthands.go`](../cmd/utils/shorthands.go), and this is the same table:

| Short | Long flag |
|---|---|
| `-o` | `--output` |
| `-y` | `--yes` |
| `-d` | `--deployment` |
| `-n` | `--name` |
| `-f` | `--follow` |
| `-a` | `--all` |
| `-h` | `--help` |
| `-w` | `--workspace` |

No other flag has a short option, visible or hidden, outside the passthrough commands. A flag keeps its letter only under the long name the table gives it, and a command that has one of these flags takes its letter too. A new flag is spelled long: it never takes a letter, and a letter is never reassigned.

- **A letter is withheld where 1.x gave it to another flag on that command**, so a 1.x script that typed it is refused by name instead of read as something else. `astro deploy -d` was `--dags`, `astro deployment hibernate -d` was `--for`, `astro deployment logs -w` was `--warn`, and `astro deploy -w` was `--wait`, and on APC `deployment create` and `update` -n was `--nfs-location`, a flag 1.x registered only where the platform mounts NFS: it is in the inventory with the other conditional flags, and has a `removedFlags` entry with a `shorthand` that names both flags. `deployment token create` and `update` give up -d (`--description`); the other token commands have it. `astro deploy` and `astro deploy bundle` never give `-w` to `--workspace`, in any tree, and refuse it with `-w was removed in Astro CLI v2: use --wait` for as long as v2 lives (the `removedFlags` entry with a `shorthand`, which answers for the letter alone). `-o` is the one letter whose 1.x meaning differs on purpose: `astro organization audit-logs export -o` was `--output-file`, and says where the path goes now.
- **A hidden 1.x alias takes no letter.** `--deployment-id`, `--deployment-name`, `--workspace-id` and `--label` (`utils.AddAlias`, `AddOneXNoOp`) are registered without the shorthand 1.x gave them. 1.x's `-d` and `-w` for the Deployment and workspace ids are `--deployment`'s and `--workspace`'s letters, the same flags; any other letter is refused with the long flag to type (`astro deployment hibernate -n` says `use --deployment`, and `astro workspace create -l` on APC says `use --name`).
- **Every removed letter says what replaced it.** A letter 1.x had on a command (the inventory, `v1_flags.tsv`) that v2 does not has a message, as the removed flags do: naming the long flag when the command still has it, or the registry entry of the flag that went (`-t was removed in Astro CLI v2: use --name`). A letter v2 introduced and took away before the release needs none.

**The API passthrough commands are exempt.** `astro api` (every subcommand: `airflow`, `cloud`, `registry`, `ls`, `describe`), `astro af` and `astro local af`, and `astro local api` mirror tools whose users and agent skills already type their letters: gh api (`-X`, `-H`, `-F`, `-f`, `-i`; Vercel's `vercel api` keeps the same), and the standalone af CLI. They keep every letter they had in 1.x and in earlier v2 builds, with the meaning they had; nothing about them changed from 1.x. Each is a family with a table of its own in `cmd/utils/shorthands.go`, `utils.APIShortOptions` (`-X --method`, `-F --field`, `-f --raw-field`, `-H --header`, `-i --include`, `-q --jq`, `-p --path-param`, `-t --template`, `-v --verbose`, `-u --username`, `-O --organization-id`, `-W --workspace-id`) and `utils.AfShortOptions` (`-X`, `-F`, `-H`, `-i`, `-v` as above, plus `-c --conf`, `-l --limit`, `-m --map-index`, `-p --poll-interval`, `-r --run-id`, `-s --state`, `-t --tags`). A command belongs to a family by its path below the root (`utils.PassthroughPaths`: `api`, `af`, `local af`, `local api`), so a command added under one takes the exemption by itself, and cannot take any letter outside the family's table and the main one. Within a family a letter means one thing; the two families differ on `-t` (`--template` against `--tags`) and `-p` (`--path-param` against `--poll-interval`), as gh api and af always did. The main table still applies on an exempt command for the letters its family does not have, so `-d`, `-o`, `-h` and the rest mean what they mean everywhere. Where a family has the letter it wins: `-f` is gh api's raw field on `astro api`, not `--follow`.

`TestShortOptionsFollowTheTable` holds every flag in every tree to the table (the exempt commands to their family's, with the main table behind it), and fails on a new flag that takes a letter. `TestTableLettersReachEveryFlagThatCanTakeThem` fails on a command that has one of the table's flags without its letter, unless 1.x gave the letter to another flag there or `lettersWithheld` says why. `TestNoShortOptionIsReadAsAnother1xFlag` fails on a letter that 1.x gave a different flag on the same command, and `TestEveryV1FlagStillWorksOrSaysWhatReplacedIt` fails on a 1.x letter that is neither the same flag's nor refused. `TestShortOptionsTableIsDocumented` keeps this table and the code's the same.

### Deprecated spellings

A spelling that still works but that v2 means to drop says so, once per run, through one helper: `cliout.WarnDeprecated` in [`cmd/cliout/deprecated.go`](../cmd/cliout/deprecated.go). The line is on stderr, led by the usual yellow `Warning:`, and names what was typed and what to type instead:

```
Warning: --deployment-id is deprecated: use --deployment
```

- **Once per run per distinct spelling.** Two different old flags give two lines, the same one typed twice gives one. `cliout` remembers what the run has said (`cliout.WarnOnce`, which `WarnDeprecated` is made of), and `cliout.Execute` clears that as a run starts (`ResetWarnOnce`), so a second run in one process says it again. A warning that is no deprecated spelling but is as much the run's, such as the notice that `ASTRONOMER_KEY_ID` and `ASTRONOMER_KEY_SECRET` are set and no longer used, goes through `WarnOnce` too.
- **Stderr only.** Under `--output json` stdout is still exactly one document, the result or the error object, on a success or a failure alike, and the line is on stderr either way, as with every other warning (progress, warnings and notes go to stderr, see [Adding `--output` to a command](#adding---output-to-a-command)). The JSON is unchanged and has no `warnings` key for it.
- **No suppression, no effect on the exit code.** Nothing turns the line off: the `ASTRO_RENAME_HINTS_DISABLED` variable that hid the old, longer hint is gone. A run that works exits 0 with the line, and one that fails exits as it would have.
- **Removed spellings do not warn.** They fail with their removal message (see [Removed 1.x commands and flags](#removed-1x-commands-and-flags)) before anything is used. A spelling that is simply supported, such as `ls` for `list`, is not deprecated and says nothing; no kept command alias is deprecated. A 1.x flag a command accepts and ignores (`--workspace-id` on `astro deployment team`, `astro deploy --force`) is no spelling of anything and has no replacement to name, so it says nothing either.

What is deprecated:

- **The hidden 1.x flag aliases.** `utils.AddAlias` (`--deployment-id`, `--deployment-name`, `--workspace-id`, `--label`, `--search`) marks the alias with `cliout.DeprecateFlag`, which records what to type instead (`use --deployment`) and hides the flag. `utils.ApplyPreferredFlags`, which every Astro and APC command runs once its flags are parsed, hands the alias's value to the flag it stands for and then warns of each alias the run gave (`cliout.WarnDeprecatedFlags`). The same step queues the renamed-flags telemetry event, which is what tells us when an alias can go. An alias given as `""` still means the default, as in 1.x, and is deprecated all the same.
- **A flag deprecated in v2** takes the same mark (`astro local env … set --secret`), and the command that reads it calls `cliout.WarnDeprecatedFlags` with its own stderr.
- **A kept 1.x subcommand**: APC's hidden `astro deployment logs scheduler`, `webserver` and `workers` still run, and warn, naming the spelling typed (an alias such as `sch` too) and `astro deployment logs --scheduler`.
- **A deprecated verb**: a command that v2 renamed or folded into another keeps its old spelling as a hidden command that still runs, through `cliout.DeprecateCommand`, which marks it, hides it and warns once per run with the arguments check (so a run that is later refused, or a test that replaces every run, still says it). The token groups' verbs moved up a level, one flat set per token command, so `astro workspace token organization-token add` (the hidden group and each of its verbs), `astro deployment token workspace-token …` and `organization-token …` warn `astro workspace token organization-token add is deprecated: use astro workspace token add`; and `delete` of `astro env <noun> link` is `remove`, so `astro env variable link delete` warns to use `astro env variable link remove`. Their `--org-token-name` and `--workspace-token-name` flags are `utils.AddAlias` aliases of `--name`. A warning adds to the path when the new verb is not quite the old one (the flat `list` shows every scope, and the flat `remove` asks to confirm where the old never did, so it says `remove --yes`). Each use is recorded as the flag aliases are (`telemetry.RecordRenamedFlags`, the old path beside the new, in the same event as the verb's own flag aliases).

`TestEveryDeprecatedVerbWarnsOncePerRun` and `TestDeprecatedVerbsAreHiddenAndTheirReplacementsAreNot` in `cmd` hold each deprecated verb to its table (`deprecatedVerbs`): the line it says in each tree, once per run, its hiding in help, and that what it names exists and shows. `TestEveryDeprecatedAliasWarnsOncePerRun` in `cmd` walks every command of every tree for the aliases it takes, types each twice, and checks that each warns exactly once, that nothing reaches stdout, and that `--output json` leaves stdout one document. `TestEveryDeprecatedFlagIsAnAliasOrHasItsOwnTest` fails on a deprecated flag that is neither an alias nor listed with its own test, and `TestOnlyKept1xSubcommandsAreDeprecatedCommands` on a command that uses cobra's own `Deprecated` or a kept subcommand nobody listed.

## Help

Every `--help` page is drawn by one renderer, [`cmd/help.go`](../cmd/help.go), which the root installs with `SetHelpFunc` and `SetUsageFunc` and every command inherits. It wraps prose and flag descriptions to the terminal (at most 100 columns, 80 when piped), lists each command with its aliases, and puts examples after the flags they use. It shows the current context only on commands that run the platform pre-run, so not on the offline core tree. A command does not set a template of its own: the inherited func would ignore it. A section a command needs belongs in the renderer instead, as flag groups do. Annotate a flag with `group` to list it under `<Group> Flags:`, and set `flag-groups` on the command to order those sections (`astro deploy` does both).

What goes into a page is checked by `TestHelpFollowsTheStyleGuide` in [`cmd/help_lint_test.go`](../cmd/help_lint_test.go). It reads the same trees every tree-wide test in `cmd` does (aliases, groups, shorthands, `--output`, the error contract): `rootsUnderTest` in [`cmd/roots_test.go`](../cmd/roots_test.go) builds one for each configuration in its `treeConfigs` table, setting up each one's config immediately before building it. They are Astro for a non-hosted organization and for a hosted one, whose `deployment create` and `update` gain flags of their own, and APC under an APC context at three platform versions: the newest any gate in `cmd/apc` asks for (where `deployment adopt`, `create --mode` and `deploy --dags` appear), one below every gate (where the pre-1.0.0 examples do), and 1.0.0 between them. Between the newest and oldest, both sides of every version gate are built. Lists that excuse commands are keyed by platform and apply to each of its trees. A test that runs a tree rather than reading it uses `treesToExecute`, the two whose surrounding state (`cmd/apc`'s package-level platform version, the config) is still theirs once all five are built. `TestAPCTreesStraddleEveryGate` parses `cmd/apc` for every `houston.VersionRestrictions` literal (the command-availability table's entries among them) and every `VerifyVersionMatch` call, and fails when a gate falls outside them, is not a `GTE`, or gives its version as anything but a literal it can read.

- A command's `Short`, and a flag's description, start with a capital and do not end in a period.
- A top-level command's `Short` fits on its row of the root page at 100 columns. The room is what the renderer leaves after the command column, which the widest spellings size (`deployment, de, deployments`), so it moves when they do.
- A positional argument in `Use` is `<UPPER_SNAKE>` when required and `[UPPER_SNAKE]` when optional, with `...` for one that repeats, as in `astro af runs get <DAG_ID> <RUN_ID>`. Arguments handed on as they are after `--` are spelled `[-- COMMAND...]` (any UPPER_SNAKE name), last, as in `astro link add [NAME] [-- COMMAND...]`.
- A runnable leaf command has an `Example`. Examples are command lines indented two spaces with no `$ ` prompt, so they paste as they are, and any explanation goes on a `  # comment` line above the command. A command line may set environment variables before `astro` (`ASTRO_LOCAL_HEALTH_TIMEOUT=10m astro local start`).
- An example line is at most 100 columns, since examples print as written and are never wrapped. A longer command ends its line with ` \` and continues on a line indented four spaces. Nothing may follow the backslash: with a space after it, a shell runs the next line as a command of its own. A line indented four spaces is a continuation, so it must follow a line ending in ` \`, and a line ending in ` \` must be followed by one.
- Every `astro …` line in an example names a command that exists in that tree, with flags it accepts and an argument count its `Args` validator allows. Nothing runs; placeholders such as `<DEPLOYMENT_ID>` count as arguments, a line continued with ` \` is joined first, leading `NAME=value` words are skipped, and every command on a line that runs astro is checked, after `|`, `||`, `&&` or `;` as well as at its start.
- A paragraph of a `Long` is one line, with a blank line before the next: the renderer wraps it, so a paragraph broken by hand renders with a short line in mid-sentence. A list of `- ` items, or an indented literal, starts after a blank line or a heading ending in `:`, and list items follow one another directly; any other line directly after another is a paragraph broken by hand, including one sentence per line. The renderer hangs a list item's continuation itself, so an item is one line too. Indented lines are left as written.
- A `Short`, a `Long`, an example or a flag's description writes a command, flag or path as plain text, with no backticks (see [Commands in messages](#commands-in-messages)); `TestHelpHasNoBackticks` fails on a page that prints one.

The commands that failed a rule when it was written are listed per rule in [`cmd/help_exceptions_test.go`](../cmd/help_exceptions_test.go). That list only shrinks: fix a command's help and delete its line, and `TestHelpExceptionsOnlyShrink` fails on a line left behind. A new command meets the rules rather than joining the list. Every list is empty today.

## Local state

| path | what | lifetime |
| --- | --- | --- |
| `<project>/pyproject.toml` | the manifest, parsed by `pkg/manifest` | authored, committed |
| `<project>/.venv/` | the project environment | derived, gitignored |
| `<project>/.env` | plain project values (see [secrets.md](secrets.md)) | per-machine, gitignored |
| `<project>/.astro/standalone/` | a standalone Airflow's `AIRFLOW_HOME`: metadata database, logs, generated admin password | per-machine, gitignored |
| `~/.astro/` | durable per-user state: auth and config (`config.yaml`), the vault (`secrets/`), the proxy (`proxy/`) | durable |
| `~/.cache/astro/projects/<id>/` | rebuildable runtime state (`$XDG_CACHE_HOME/astro` when set) | rebuildable |

A project's id is the sha256 of its canonical path (`localrt.CanonicalPath`): absolute, symlinks resolved, and each component spelled the way the filesystem spells it, so differently-cased spellings of one directory are one project. Hostnames are display labels, not keys.

The project's cache directory holds two files that never merge:

- `runtime.json`, the record of a running Airflow, owned by `pkg/localrt` and shared by both engines. Fields: `projectPath`, `mode`, `pid`/`pgid` (standalone: the supervisor and its process group; signals and liveness address the group, because Airflow's components outlive the supervisor during shutdown) or `composeProject` (docker, plus the starter's `pid` with stop-with-session), `port`, `hostname`, `airflowMajor`, `startedAt`, `stopWithSession`. It is v2-only, so fields can be added freely.
- `state.json`, per-user preferences (`internal/userstate`), such as the `astro use` selection. userstate rewrites it canonically and would drop foreign fields, which is why the two are separate.

Tools coordinate through disk, not through each other: any of them can reconnect to, inspect or stop an Airflow another started. Whether an Airflow outlives its starter is `StopWithSession` on the plan: false by default (it keeps running), true to stop it when the starting process exits.

### Route pruning across owners

`pkg/proxy` prunes `routes.json` on every write, and two owners write it: the CLI and Astro Desktop. A route's stored PID and its owner's live PID drift apart when the owner restarts, so a plain PID check would let one owner drop a route whose Airflow is still running.

The rule: **a route is never evicted while its runtime record reports the runtime alive by that mode's own liveness check.** `pkg/localrt` builds its proxy stores with this predicate (`proxy.WithRouteLiveness`), resolving each route to its record by project path:

- Standalone: kept while the recorded process group (`pgid`, else `pid`) is alive.
- Docker: never pruned by PID, since containers outlive their starter. A docker route is removed only by a stop or by `astro local list --clean`, which checks real compose state.
- No matching record (a route a 1.x CLI wrote, or a project directory that is gone): the route's own PID check, with docker routes kept.

The predicate arrives from outside, so `pkg/proxy` has no astro-cli imports. It costs a record read and a signal, no container-engine call. Stores built outside `pkg/localrt` (the proxy daemon itself, Otto's config) use the default PID check.

### The proxy port and astro 1.x

The proxy serves on 6563. astro 1.x runs its own proxy (`astro dev proxy serve`) on 6563 from the same `~/.astro/proxy` directory and `routes.json`, so one proxy serves the projects of both. When the CLI's daemon starts and a 1.x proxy holds 6563, the daemon stops that proxy and serves there itself. It stops a process only when that process runs `dev proxy serve` for 6563, reads the same route store (from its `ASTRO_HOME` or `HOME`), and answers like an astro proxy; never Astro Desktop's proxy, its own daemon, or a process it cannot identify. In that last case the daemon falls back to another port, saves it in `proxy.fallback-port`, and tries it first on the next start, so URLs stay stable. A 1.x CLI that later finds this daemon's record stops it and takes 6563 back, and the next v2 start does the same in return; each set of projects stays reachable on 6563 either way.

### Listing and cleanup

`astro local list` enumerates every record under the cache root, reports each through its engine's liveness (docker asks the container engine, standalone checks the group), and joins live routes for a hostname. A record with no live runtime is shown as `stopped (stale)` with `--all`, and hidden by default. `astro local list --clean` removes every stale record and its route, machine-wide. It lives on `list` rather than `reset` because `reset` acts on one project (stop plus wipe).

### Compose overrides

Docker mode reads a project's `docker-compose.override.yml` (not the `.yaml` spelling) and passes it to compose as a second `--file` after the file it generates, so compose merges the two by its own rules and resolves `${VAR}` from the shell and the project's `.env`. The names `astro dev` used are kept, so a 1.x project's override still works: the `airflow` network, and the services `postgres`, `scheduler`, `triggerer`, `dag-processor` and `api-server` (Airflow 3) or `webserver` (Airflow 2). A service with `profiles:` does not start unless the shell sets `COMPOSE_PROFILES`. Stop and reset address the compose project by name, so they take the override's containers, networks and (on reset) volumes down too. Standalone mode runs no containers: it ignores the file and warns once at start.

## Platform support

Windows runs Docker mode only. Standalone mode is macOS and Linux. The proxy daemon in `pkg/proxy` runs on all three, but `astro local` starts it only on macOS and Linux for now, so on Windows a project is reached on its direct localhost port.

## Dev-mode Airflow defaults

A local Airflow is configured for someone developing DAGs, in both modes unless noted:

- **DAGs are created unpaused but run only when triggered.** `AIRFLOW__CORE__DAGS_ARE_PAUSED_AT_CREATION=False` and `AIRFLOW__SCHEDULER__USE_JOB_SCHEDULE=False`: the scheduler creates no runs of its own, so nothing runs on a cron clock and asset-triggered DAGs do not cascade, while a run triggered from the UI, `astro local af runs trigger` or the API starts at once. Paused-at-creation protects a shared scheduler from a DAG nobody reviewed; locally the author is watching, and a triggered run on a paused DAG only sits queued. `astro local start` and `restart` say schedules are off, and how to turn them on, unless the project already did.
- **Fast DAG rescan.** Each file is re-parsed every 3 seconds (`MIN_FILE_PROCESS_INTERVAL=3`) and the folder listed every 2, so a saved change shows within about 5 seconds at 1–2% of a core.
- **Zero default task retries** (standalone mode).
- **Loopback only.** Standalone binds the API server and webserver to 127.0.0.1; Docker mode publishes its ports on 127.0.0.1.

A project that sets one of these keys itself, in its `.env` or vault (or, in standalone, its shell), keeps its own value. The loopback bind is the exception, because it guards the instance rather than states a preference.
